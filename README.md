# Portfolio — 윤준식 · 백엔드 개발자

**반복되는 운영 문제를 플랫폼과 AI 에이전트로 없애는 백엔드 개발자입니다.**
개발 경력 2년 4개월(물류 IT 백엔드 1년 9개월). 입고부터 정산까지 물류 업무 전반의 시스템을 C#, ASP.NET Core, MS SQL Server로 설계하고 운영해 왔습니다.

이 저장소는 기술경력서의 대표 프로젝트를 **배경, 담당 역할 및 실행, 성과** 순서로 설명하고, 그 근거가 되는 코드를 함께 보여 주기 위한 것입니다.

> **읽는 법** — 각 프로젝트 폴더의 `README.md`에 설명과 "코드 안내" 표가 있습니다. 하위 폴더 번호(`1.`, `2.`, …)는 코드 안내의 절 번호와 같습니다. 스케줄러와 오케스트레이션 폴더에는 설계 이유를 따로 정리한 `ARCHITECTURE.md`가 있습니다.
>
> **범위** — 이 저장소의 코드는 모두 직접 구현한 코드 원문이고, 회사·브랜드·DB·서버 이름 같은 식별 정보만 일반화했습니다. 설계가 드러나는 파일만 골라 옮겼고 업무 지식 문서, 계정 스크립트, 운영 접속 정보가 담긴 설정 파일은 올리지 않았습니다. 빌드·실행이 아니라 **설계와 구현 방식을 읽기 위한** 저장소입니다.

### 1. 통합 스케줄러 플랫폼 · [`src/01.UnifiedScheduler/`](src/01.UnifiedScheduler/)

- **배경**: 20여 개 스케줄러 프로그램이 제각각 배포되어, 브랜드를 하나 추가할 때마다 코드 수정과 재배포가 필요했습니다.
- **담당 역할 및 실행**: 스케줄 설정을 코드에서 DB로 옮기기로 하고, 이를 담을 DB 스키마와 백엔드 구조를 처음부터 설계했습니다. 기본값 위에 브랜드별 설정만 덮어쓰는 2계층 상속 구조를 고안하고, 등록부터 알림까지 이어지는 8단계 실행 파이프라인과 공통 Job 베이스를 구현했습니다.
- **성과**: 브랜드 추가가 재배포에서 설정 등록으로 바뀌었습니다. 스케줄 업무 80종, 고객사 브랜드 30여 개를 배포 없이 운영하며, 누적 135만 건을 시스템 장애 없이 성공률 100%로 처리했습니다.
- 설계 결정과 이유는 [설계 문서](src/01.UnifiedScheduler/ARCHITECTURE.md)에 있습니다.

### 2. WMS 오류 진단 에이전트 (MCP) · [`src/02.DiagnosisAgent/`](src/02.DiagnosisAgent/)

- **배경**: 현장 문의(VOC)가 들어올 때마다 개발자가 화면 코드, 프로시저, 운영 데이터를 손으로 따라가며 원인을 찾아야 해 건당 2~3시간이 걸렸습니다.
- **담당 역할 및 실행**: 소스, 운영 DB, 서버 로그를 스스로 조회해 원인 위치와 근거를 보고하는 진단 에이전트를 설계했습니다. 관리자 페이지의 대화 화면과, 개발자 각자의 AI 코딩 도구에서 쓰는 MCP 서버 두 경로로 구현했습니다. 데이터 변경은 DB 권한과 SQL 검사기로 원천 차단하고 조회 내역은 감사 기록으로 남깁니다.
- **성과**: 원인 파악 시간을 건당 2~3시간에서 평균 5분 이내로 줄였고 팀의 상시 도구로 정착했습니다. 기존에 놓치고 있던 반품 확정 로직의 결함까지 찾아내 시스템 개선으로 이어졌습니다.

### 3. WMS 오케스트레이션 플랫폼 (MSA 전환) · [`src/03.WmsOrchestration/`](src/03.WmsOrchestration/)

- **배경**: 모놀리식 API로는 WMS와 외부 쇼핑몰, 물류 시스템 사이의 대량 데이터 연동을 견디기 어려웠습니다.
- **담당 역할 및 실행**: 요청을 메시지로 받아 비동기로 처리하는 오케스트레이션 구조를 설계했습니다. 대량 요청을 Job, Chunk, Step 3단계로 나눠 병렬 처리하고 Saga State Machine으로 흐름을 제어했으며, 중복 처리 방지와 재시도, 분산 락을 공통 계층에 구현했습니다.
- **성과**: 파일럿 테스트 기간 동안 타임아웃, 네트워크 장애, DB 락이 겹치는 상황에서도 서버 응답 장애 0건을 달성해 MSA 전환 가능성을 확인했습니다.
- 설계 결정과 이유는 [설계 문서](src/03.WmsOrchestration/ARCHITECTURE.md)에 있습니다.

## 공통 설계 원칙

프로젝트마다 형태는 다르지만 같은 원칙이 반복됩니다.

- **변하는 것은 설정과 문서로, 변하지 않는 것은 공통 계층으로.** 스케줄러의 2계층 설정 상속, 진단 에이전트의 지식 문서 분리, 오케스트레이션의 Consumer 베이스 클래스가 모두 같은 결정입니다. 새 브랜드와 새 업무 지식은 코드 수정 없이, 새 도메인은 업무 로직만 작성하면 추가됩니다.
- **실패가 번지지 않게 막고, 다시 실행해도 안전하게 만든다.** 스케줄러는 큐마다 워커를 따로 두어 한 작업의 지연이나 실패가 다른 큐로 번지지 않습니다. 오케스트레이션은 요청을 Step 단위로 나눠 한 Step의 실패가 전체를 멈추지 않게 했고, 같은 메시지가 두 번 와도 한 번만 처리합니다.
- **운영자가 개발자 없이 대응할 수 있게 한다.** 스케줄러의 일시정지, 수동 실행, 테스트 모드와 관리 콘솔, 원인 위치를 대신 찾아 주는 진단 에이전트가 여기에 해당합니다.
- **안전장치는 프롬프트가 아니라 구조로 만든다.** 진단 에이전트의 읽기 전용은 모델에게 부탁하는 것이 아니라 DB 계정 권한과 SQL 검사기로 강제하고, 접근 제어와 감사 기록으로 뒷받침합니다.
